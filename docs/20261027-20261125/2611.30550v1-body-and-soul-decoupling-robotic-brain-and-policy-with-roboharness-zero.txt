Abstract
Vision-language-action (VLA) policies can execute individual skills but fail to com-
plete tasks that require combining several of them. In our audit of Xiaomi-Robotics-1,
an estimated 43% of failures involve choosing the wrong target or losing track of
task progress. Wrapping a frozen VLA in a vision-language model (VLM) harness is
a natural remedy. Existing harnesses can gain substantially from task- and policy-
specific preparation, raising the question of how much of that gain transfers to a new
task or policy. An ideal harness should (i) need minimal preparation for a new task,
(ii) need no redesign for a new policy, and (iii) preserve standalone capabilities the
policy already has. To the best of our knowledge, our RoboHarness-Zero is the first
harness built this way. Its premise is that choosing targets and tracking progress
are easy for a VLM such as GPT-6 without task preparation, while the frozen VLA
already handles continuous, contact-rich motion. The frozen VLA therefore executes
continuous control while the VLM plans zero-shot and monitors execution; when
progress stalls or targets drift, the VLM first rephrases the instruction and, only
as a fallback, executes short generated code over generic motion primitives before
returning fine control to the VLA. The supervision rules stay fixed across policies,
requiring only a thin interface adapter and an automatically profiled skill config-
uration per policy. On 200 RoboCasa365 scenes, RoboHarness-Zero with GPT-6
Astra raises the success rate of frozen Xiaomi-Robotics-1 from 57.5% to 70.5% and
preserves 90.4% of its standalone successes (104/115) while rescuing 37 of 85
failures. On a shared 50-scene subset, the same rules add 8 to 10 percentage points
to each of four other frozen policies, while existing preparation-based harness
systems often fail to transfer to a new policy.

how to guide the robot in a particular setting. In its few-shot RoboCasa365 evaluation, Harness

per task and reuses it in new scenes. EmbodiedRSI (Song et al., 2026) runs robot trials to decide
which changes to its code and skills to keep, while AdaHVLA (Tang et al., 2026) revises its prompting
and recovery code separately for each robot and policy. How much of the resulting gain survives when
the task set or the policy changes? Although Harness VLA gains 29.2 percentage points on RLDX-1,
transferring its released task memories to Xiaomi-Robotics-1 on our 50-scene benchmark solves 29
scenes, compared with 30 for Xiaomi alone (−2.0 percentage points).
We argue that an ideal harness should (i) need minimal preparation for a new task, (ii) need no redesign
for a new policy, and (iii) avoid breaking what the policy already solves. We introduce RoboHarness-
Zero, a VLM harness that gives a frozen VLA the full task and monitors progress within each substage
during execution, without interfering while the policy advances. When progress stalls or the robot
acts on the wrong target, RoboHarness-Zero first revises the instruction and, if needed, briefly takes
over the arm via VLM-generated code over generic motion primitives before handing control back.
Our core insight is that the instruction and the scene alone determine which object the robot should
act on, what must happen next, and whether the current step is complete, so a VLM can judge them
zero-shot and identically across policies. This allows RoboHarness-Zero to supervise different tasks
and frozen VLA backbones during execution with a single fixed set of rules; onboarding a new policy
requires no task-specific demonstrations or scripts—only a thin interface adapter and a one-time
automatic calibration (§3).

2. Related Work
2.1. VLM harnesses for robot manipulation
Language models can guide manipulation through a learned hierarchy, as in Steerable VLA (Chen
et al., 2026a), Hi Robot (Shi et al., 2025), and 𝜋0.5 (Black et al., 2025), or by calling robot skills and
motion primitives directly, as in SayCan (Ichter et al., 2023), Code as Policies (Liang et al., 2022),
Show-Harness (Chen et al., 2026b), Robo-Harness K1 (Li et al., 2026), and HexaShell (Gao et al.,
2026). A third approach places a harness around a frozen action policy. We relate these harnesses to
the three properties of an ideal harness (§1).
Most harnesses need preparation before they can be used on a task, contrary to property (i). On
RoboCasa365, Harness VLA (Zhang et al., 2026b) explores one reference scene per task and stores a
successful sequence of primitives that its planner can reuse, calling the VLA for contact-rich steps.
HarnessPAI (Wang et al., 2026a) instead uses a coding agent to revise a separate control program for
each task between trials. SERA (Du et al., 2026) evaluates harness revisions through environment
rollouts, while EmbodiedRSI (Song et al., 2026) uses robot trials to select changes to code and skills.
Cracking Mobile Manipulation (Wang et al., 2026b) uses demonstrations to guide planning and uses
separate interventions to correct base positioning and local manipulation. Preparation also underlies
the top RoboCasa365 leaderboard entry, HexaShell (Gao et al., 2026), which represents a separate,
policy-free line of work where a VLM controls the robot directly by writing code over motion and
perception tools. Drafting a one-page skill from earlier runs for each of the 50 tasks—recording
judging criteria, step flow, and measured parameters—lifts HexaShell from 59.3% with no task-specific
input to 85.6%; by contrast, our work focuses on harnessing existing frozen VLAs without per-task
preparation.
Few harnesses carry one design across policies, as property (ii) requires. AdaHVLA (Tang et al., 2026)
specializes its coordination rules to each robot–executor pair. On RoboCasa365, PhyAgentOS (Liu
et al., 2026a) applies a common verifier to three frozen policies after the initial rollout fails, at which
point it can issue a recovery instruction from the robot’s current state. Because it waits for the episode
to fail, it does not put the policy’s existing successes at risk, but it also cannot act while an error is
still reversible.
Our harness gives the frozen policy the full task instruction and leaves it in control by default, while
the VLM monitors each substage during execution. If progress stalls or the robot selects the wrong
target (Figure 2), the VLM can intervene while the error is still reversible. A one-time calibration lets
the same supervision rules transfer to a new policy without retraining, per-task demonstrations, or
exploratory rollouts on the evaluation tasks. To our knowledge, none of the harnesses above separates,
on paired runs, the successes it preserves from the failures it rescues; we report both (§4.1).

2.2. When and how to intervene
When should a harness intervene, and what should it change? Building on earlier work on language
feedback (Huang et al., 2022; Guo et al., 2024), Mostly Harmless (Jeong et al., 2026) learns to
rewrite instructions and retains the original when a calibrated predictor finds little evidence that
rewriting will help.
Many recovery methods act directly on motion. ForkCast (Wen et al., 2026) selects among continuing,
changing viewpoint, and replanning the arm trajectory. CheckVLA (Liu et al., 2026b) verifies actions
with a trained world model, while IDR (Zhang et al., 2026a) refines actions across several frozen
policies without training. IDR adjusts every action the policy produces; our harness leaves the policy’s
actions untouched unless a substage stalls or the target is wrong, and gives an off-the-shelf VLM
responsibility for deciding when and how to intervene. Tracking the current substage against the
full instruction lets it recognize a precise grasp of the wrong object, revise the instruction first, and
escalate to a bounded takeover when needed.
RESCUE (Ahmedt-Aristizabal et al., 2026) compares alternatives from the same checkpoint and
shows how unnecessary intervention can disrupt success. Hi-VLA (Hu et al., 2026) finds that reliable
controllers still benefit from orchestration. StageCraft (Pangaonkar et al., 2026) finds that stronger
policies need fewer scene adjustments. These findings are compatible: selective intervention can
preserve existing successes while timely correction can rescue failures. Our evaluation measures both
effects separately, as retention and rescue (§4.1).
2.3. Failure detection
SAFE (Gu et al., 2025) predicts failure on unseen tasks from a VLA’s internal features, while external
monitors judge success from images or learn from teleoperator interventions to flag mistakes (Du et al.,
2023; Sa et al., 2026). A detector can flag repeated unsuccessful grasps as they occur, but the alarm
alone leaves open how to recover (Ma et al., 2026). RESCUE (Ahmedt-Aristizabal et al., 2026) shows
that alarms can arrive too late or prompt unnecessary intervention, and Soddy et al. (2026) predict
MemoryVLA failures early yet find that none of four interventions reliably improves success. Our VLM
judges progress on the current substage from images and robot state without per-policy detector
training, and our analysis of what follows an alert likewise identifies recovery as the bottleneck.
3. RoboHarness-Zero: A Fixed Harness for Any Frozen Policy
3.1. VLAs fail on decisions, not only motions
We audited 193 of the 893 failed rollouts from an earlier RoboCasa365 evaluation of Xiaomi-Robotics-1
running without a harness, sampled across five task groups (Appendix B.4).
After weighting by the number of failures in each task group, we estimate that 43% of failures involve
a decision error. The robot chooses the wrong target in 24% of failures and loses track of task order or
progress in 19% (an order or progress error). The remaining 57% comprise physical execution failures
(53% of all failures), episodes that exhaust their step budget while still making progress (3.7%), and
violations of a task constraint (0.3%). We distinguish two types of execution failure according to
whether the policy has ever completed the same task in another trial: inconsistent execution when it
has, and execution with no observed task success when it has not. Table A.2 in the appendix gives the
definition and an example of each category.
These findings motivate our focus: using a VLM to ground the policy’s decisions in the instruction
and the current scene. The VLM does so both when selecting the intended target and when judging

whether the robot is ready to move on to the next step.
3.2. Overview and design principles
Figure 3 illustrates how RoboHarness-Zero divides control between a frozen VLA and a supervising
VLM. The VLA receives the task instruction and generates robot actions in short sequences. At
checkpoints, the VLM sees the left, right, and wrist camera views, the poses of the base and end
effector, and the gripper positions. It interprets these observations in light of the original instruction,
its current plan, and the commands executed since its last review. When the environment detects that
the whole task has succeeded, the harness ends the episode at once and records a success. Before
that, it receives no success signal. Intermediate judgments, such as whether the robot has grasped
the intended object, must be made from the available observations. The robot interface supplies no
ground-truth object poses, hidden fixture states, substage completion labels, or expert trajectory.
When the evidence is ambiguous, the VLM can call perception tools—or short generated code—to
inspect a fresh view, zoom in, or back-project depth at a visible pixel into 3D. If the policy is making
progress, it continues under the same instruction. If the VLM identifies a wrong target or a stalled step,
it first revises the instruction and observes how the policy responds. When a takeover is warranted,
the harness authorizes a limited sequence of base, torso, arm, or gripper motions, which consume the
same episode budget as policy actions; the VLM then checks the result in a fresh observation and
returns control to the VLA.
RoboHarness-Zero is designed around the three properties of an ideal harness (§1). For property (i),
minimal preparation for a new task, the VLM forms its own plan from the instruction and the scene in
each episode, so the harness uses no task-specific demonstrations or scripts (§3.3). For property (ii),
no redesign for a new policy, the supervision rules stay fixed and a new policy brings only a native
adapter and a skill profile (§3.7). Property (iii), breaking nothing the policy already solves, depends
on when and how the VLM intervenes.
The choice of when to intervene matters because supervision can change outcomes in either direction.

3.3. Hand over the whole task, then watch
RoboHarness-Zero needs no preparation for a new task: every episode starts from the task instruction
alone, with no demonstrations, memories of earlier episodes, or task scripts (Appendix B.6). At the
start of a composite task with no whole-task entry in the skill profile, RoboHarness-Zero passes the
original instruction verbatim to the frozen VLA; most composite tasks in our evaluation fall under
this rule, while tasks matching a profiled entry adjust only the initial check interval and takeover
permissions according to measured reliability (Appendix B.6). The VLM uses its own plan to identify
what would count as progress at each substage. Reaching a new substage updates what the VLM
watches for, while the policy continues under the original instruction.
Monitoring takes place between windows of policy execution. Xiaomi-Robotics-1 generates 16 actions
per prediction. A default window allows ten predictions, or 160 control steps (eight seconds of
simulated motion). At a checkpoint, the VLM can inspect fresh left, right, and wrist views alongside
the robot state and the actions executed since its last review. Its default response is to let the policy
continue, without sending a new instruction or motor command (Appendix B.7 gives an example).
If the VLM issued the steps one at a time, each transition between steps would depend on its judgment.
Keeping the substage plan on the monitoring side lets the policy carry out that transition itself while
the VLM checks the result (Appendix B.7).

3.4. Progress is judged at the current substage
While the policy executes, the VLM asks one question at each checkpoint: has the robot made progress
on the current substage? The VLM’s plan divides the task into substages and each substage into one
or more phases, such as approaching an object and then grasping it. Each phase has a target, the
object or location it acts on. In the peeler episode of Figure 2b, reaching the utensils completes the
approach phase, but the grasp phase stays incomplete while the peeler remains below the counter
edge. The harness records progress for the current phase and its target. The first 3D distance estimate
from the end effector to the depth-localized target establishes a reference. A fresh observation earns
progress credit when the estimated distance falls at least 2 cm below its previous minimum, or when
the VLM first verifies that the phase is complete. Once the robot has grasped an object, seeing it still
in the gripper confirms that the grasp is secure. Progress toward placement requires fresh evidence
about the object’s destination. Otherwise, credit for holding the object could hide a stalled placement
(Appendix B.7).
The VLM can continue, advance, or review. While the current phase is underway, the policy continues
under its existing instruction. Verified progress resets the stall counter. Otherwise, the harness adds
to the counter the number of control steps the policy has executed since the previous checkpoint.
When the VLM verifies phase completion, it advances to the next phase or, when the substage has
none left, to the next unfinished substage in its plan. At any checkpoint where the counter reaches
the policy’s stall window (§3.7), the harness raises a stall alert: the VLM reviews the remaining goal
and may give the policy a more specific instruction, while leaving low-level motor execution with the
policy rather than taking over. For Xiaomi-Robotics-1 the stall window is 120 steps, less than a full
160-step window, so one full window without verified progress triggers a review. The policy retains
motor control during this review. RoboCasa’s task-level success predicate determines when the full
task has succeeded.
3.5. Reword before taking over
When a task stalls, the first intervention available to the VLM is to change the instruction. The VLM
can narrow a multi-step request to the step where the robot is stuck, rephrase the same goal as a
short imperative, or identify the intended object by its visible color, shape, or location. In the peeler
episode, the VLM tells the policy, “Place the green-handled peeler on the cutting board,” which names
the tool to pick up. The frozen VLA still chooses how to approach, grasp, and move it. This lets the
VLM correct the policy’s interpretation of the scene through the policy’s existing language interface,
without access to its internal state or action representation.
Escalation depends on what happens when the robot acts. Two verified physical failures on the same
substage, such as two missed grasps, make a bounded takeover available. The harness carries this
count across instruction changes. Repeated rewording alone never triggers a takeover. A dropped
object, an unsafe motion, or a confirmed conflict with the task, such as grasping the wrong object,
can justify an earlier takeover. Section 4.5 reports which paired gains involve instruction rewriting
alone. Section 4.6 compares the full harness with a no-VLM control that periodically reissues the
original instruction.
3.6. Bounded takeover and hand-back
Once takeover is available (§3.5), the VLM can reposition the base, adjust torso height, and guide the
gripper through waypoints identified from camera and depth observations. In the peeler episode, the
policy delivers the knife even after the reworded instruction. The harness then guides the gripper
to the peeler and returns control to the policy, which completes the task. For skills the policy has

demonstrated it can perform, the VLM brings the hand into position and leaves fine contact to the
policy. For weak or unmeasured skills, the harness also permits direct grasping, placement, and
pouring. Closing the gripper on an object requires a fresh wrist-camera check, and the VLM must
verify after lifting that the object moved with the hand.
A takeover draws from the same episode budget as the policy. Its initial allowance scales with the
skill’s measured typical duration, with a fixed default when no measurement is available. The harness
ends the attempt when it stops making progress or upon a verified drop or unsafe motion. If the robot
is already moving a securely held object toward placement, it can receive a short, capped extension
(Appendix B.8). To hand control back, the VLM positions the base and hand so the target is visible
and within reach. It preserves any held object, reissues the instruction for the current substage, and
checks progress after a short window of fresh policy actions. Section 4.5 reports how often takeover
is used, and Section 4.7 examines where it fails.
3.7. Calibrating to a new policy
Switching policies leaves the rules unchanged, as property (ii) requires. It needs only a native adapter
and a set of measured constants (Table 1). The adapter maps camera images, robot state, and the
active instruction into the policy’s input format and returns action chunks through a common interface.
Profiling supplies three policy-specific quantities used by the fixed rules: per-skill success rates (which
govern whether takeover may grasp or place directly; §3.6), typical skill durations (which scale
takeover budgets; §3.6), and stall windows (how many steps the policy may execute without verified
progress before triggering a review; §3.4). Xiaomi-Robotics-1 served as our development policy, for
which we fixed a global 120-step stall window during development; all four transfer policies use stall
windows derived automatically from profiling with zero manual tuning.
We profile a frozen policy by running it alone on 65 atomic RoboCasa tasks on separate profiling
seeds, with 15 episodes per task. Each episode runs until the environment reports success or the task
horizon expires. For skill 𝑘, we estimate its success rate as the fraction of its 15 trials that succeed
and its typical duration as the median step of first success among those trials. The 975 rollouts take
6.16 cumulative worker-hours for GR00T N1.5, with zero VLM calls.
To set a policy’s stall windows, we use its successful profiling trajectories to estimate how long a
policy that eventually succeeds can appear to make no progress. For each trajectory 𝑖, let 𝑔𝑖be the
longest interval, in control steps, during which an offline measure of end-effector motion registers no
progress. For each skill 𝑘, we set 𝑊𝑘= max(1, ⌈1.5 𝑄0.95({𝑔𝑖: 𝑖∈𝑘})⌉), using a fixed multiplier of 1.5.
When a substage has no matching skill, we use the same calculation across all successful trajectories.
During execution, the VLM continues to judge progress from evidence about the current target and
substage, as described in §3.4. Each policy uses its own measured skill success rates and durations.
Appendix B.2 lists the stall windows used for each policy.
The fallback matters on unfamiliar task compositions. In the Sol trajectory audit (§4.1), only 16 of
261 distinct registered substages (6.1%) match a measured skill. The other 245 have no matching
entry. A policy-wide stall window therefore lets the harness adapt how long it waits even when it
cannot identify a previously measured skill.

4.4. Does a task-prepared harness transfer to a stronger policy?
Does the gain from preparing a harness for each task carry over to a stronger policy? Harness VLA
is the closest public comparison on RoboCasa365. It uses a reference scene for each task to build
a memory of how to solve that task. With RLDX-1, the reported gains over the 30.0% standalone
baseline are 27.2 percentage points with GPT-5.5 and 29.2 points with GPT-6 Astra (Zhang et al.,
2026b, arXiv v5, Table 4 and Appendix H, Table 22).
We ran the official Harness VLA code with Xiaomi-Robotics-1 and the released memories, without
collecting new traces or revising the memories for Xiaomi. Both harnesses used GPT-6 Astra at xhigh
reasoning effort on the same 50 scenes as in §4.3. Harness VLA solves 29 scenes, Xiaomi alone solves
30, and our harness solves 34 (Table 5). The two harnesses tie on atomic tasks. Our five additional
successes come from composite tasks, three on seen compositions and two on unseen compositions.
Four tasks lack task-specific notes in the released memory. Harness VLA still solves three of these
scenes, and without the four it solves 26 of the remaining 46, against 28 for Xiaomi alone and 31 for
our harness (Appendix B.9).
On RLDX-1, the policy it was prepared for, Harness VLA’s published gain of 29.2 points is about three
times ours of ten (§4.3). The standalone baselines differ, 30.0% in the published evaluation and 40%
on our 50 scenes, so we compare gains rather than absolute rates. On Xiaomi the order reverses.
With the released memories, Harness VLA retains 26 of Xiaomi’s 30 standalone successes and rescues
three of its 20 failures, ending one scene below the policy alone, while our harness retains 28 and
rescues six. Harness VLA loses successes and rescues failures at similar rates, 13% and 15%, but
Xiaomi has 30 successes to lose and only 20 failures to rescue, so the losses outweigh the rescues.
We did not rebuild the memories for Xiaomi: that is the per-policy preparation that property (ii)
asks a harness to do without, and this comparison measures what remains without it. The gain from
per-task preparation therefore does not carry over to the stronger policy here, whereas our smaller
gain holds on all five policies.

4.6. Ablations

second time yield a similar result? On the same 200 scenes, we ran the frozen Xiaomi policy through

and removes the other two: nothing judges progress and nothing intervenes.

4.7. Failure analysis
Where does supervision break down when Xiaomi loses a task it solves alone or an intervention leaves
a substage unfinished?

no second attempt is possible. This is a limitation of the tool’s implementation rather than of the

5. Discussion
The paired evaluations show that the same supervision rules can improve several frozen policies while
preserving most of their standalone successes. The practical value of this approach depends on how
much of the benefit carries over when the policy changes, how reliably the robot recovers after an
intervention, and when the gains justify the added latency of VLM supervision.
What transfers across policies. On the same 50 scenes, supervision adds eight to ten percentage
points to each of five frozen policies and preserves 58 of the 59 standalone successes across the
four new policies. Transfer requires a native adapter and a policy skill profile. We prepared no task
memories, exploratory rollouts, demonstrations, or scripts. What carries over less well is rescue: the
harness recovers 18 of 141 standalone failures on the four new policies, against six of 20 for Xiaomi
on the same scenes. The gain from per-task preparation, in our test of Harness VLA, did not carry
over to the stronger policy (§4.4).
Physical recovery remains difficult. The VLM can change what a frozen policy attempts and when
it attempts it, but the policy executes each grasp or placement with the motor skills it already has.
When the policy lacks the skill, the remaining option is takeover, and takeover generally follows a
harder failure: across all 200 scenes, 20/65 episodes involving takeover succeed, compared with
19/31 involving rewriting alone (Table 6). A takeover also ends with a handoff, after which the policy
must continue from a pose chosen by the VLM; the failed recoveries in §4.7 include five in which the
policy cannot find or select the target after the handoff. Whether future VLAs or foundation models
learn to recover on their own remains open. For the frozen policies tested here, the VLA alone still
leaves recoverable failures unresolved.
When supervision is worth its cost. Xiaomi gains only four percentage points on atomic tasks. For a
policy that already succeeds 95% of the time, even rescuing 43.5% of its failures requires retaining
about 98% of its successes to break even. Supervision averages 71 VLM requests per episode, and
waiting for responses consumes 87% of episode wall time. Given that most runtime goes to VLM
requests, which decisions need the stronger model? Sol and Astra retain nearly the same number
of standalone successes but rescue 23 and 37 failures (§4.5). This suggests a division of labor in
which a smaller model monitors routine progress and calls a stronger model when a substage needs
recovery. Supervision may also become more valuable on longer tasks: Xiaomi’s gains rise from four

points on atomic tasks to 16 on seen compositions and 20 on unseen compositions, yet an episode
averages only 57 seconds of simulated motion, and the longest lasts 3.6 minutes. Longer tasks offer
more opportunities for a recoverable error: if each substage succeeds 90% of the time, a task of 50
substages finishes only 0.5% of the time unless failed substages can be recovered.
Limitations. We developed the harness with Xiaomi, so the higher rescue rate on Xiaomi could
reflect either Xiaomi’s capabilities or design choices informed by that policy. Our transfer evidence
covers 50 simulated scenes per new policy and one competing harness. We did not compare with
EmbodiedRSI (Song et al., 2026), which learns skills and memory during exploration. We have yet
to test whether a smaller model would escalate early enough to preserve Astra’s gains. The trend
across task categories is an extrapolation because the three categories differ in familiarity as well as
complexity; testing it calls for longer, previously unseen compositions with recovery scored separately
at each failed substage.
6. Conclusion
Our harness gives a frozen VLA the full task and monitors progress at each substage, responding to
stalls by revising the instruction and, when needed, briefly taking over. On 200 RoboCasa365 scenes,
supervision raises Xiaomi-Robotics-1’s success rate from 57.5% to 70.5%, compared with 56.5% when
the harness reissues the original instruction without a VLM. RoboHarness-Zero meets the first two
properties of an ideal harness by design and comes close to the third. It needs no preparation for a
new task: the VLM forms its plan from the instruction and the scene in each episode. It needs no
redesign for a new policy: the same supervision rules add eight to ten percentage points to each of
five frozen policies on the shared 50 scenes. It breaks little that a policy already solves, preserving
104 of Xiaomi-Robotics-1’s 115 standalone successes and 58 of 59 on the four other policies. The gain
therefore survives a change of policy, whereas a harness prepared for each task does not improve the
stronger policy in our test (§4.4). Rescue rates vary with the capabilities of both the policy and the
VLM, and physical recovery remains the main bottleneck. Our next steps are to improve recovery after
failed grasps and placements, test a smaller VLM for routine monitoring, and evaluate the harness on
longer tasks and on physical robots.

B. Evaluation protocol details
B.1. Episode selection and planning timeouts
The main evaluation used the Xiaomi-Robotics-1-RoboCasa365 checkpoint (0d1aa76d) and harness
v1.2.3.5 (c8911c64). It ran on November 3–7, 2026, with a 330-second API timeout and a 180-
second default planning timeout. RLDX-1 used the RLDX-1-FT-RC365 checkpoint (c53d0bc0),
and WorldDreamer used the world_dreamer-robocasa365-multi_task checkpoint (e570a06b).
The primary Xiaomi analysis used episode indices 1–4. After outcomes for the 50 index-0 scenes
became available, we decided to exclude them from the primary summary. All 50 have verified
environment scores. The harness solves 25 and Xiaomi alone solves 24.
Ten initially unsuccessful Xiaomi–Astra runs ended early with planning timeouts. We reran those
scenes with a 600-second planning timeout in place of the 180-second default. These were all the runs
that ended on a planning timeout; such a run is cut short and can only be scored as a failure, so the
reruns were not selected by outcome. Two changed from failure to success. The harness thus solves
141/200 scenes with the reruns and 139/200 using the original scores, compared with 115/200 for
Xiaomi alone. Including index 0 gives 166/250 versus 139/250 with the reruns, or 164/250 versus
139/250 using the original scores. The separate 50-scene evaluations of the four other policies used a
600-second planning timeout and a 330-second API timeout.
B.2. Stall windows used for each policy
RLDX-1 and WorldDreamer use stall windows derived from their own profiling rollouts (§3.7). We
did not derive policy-specific windows for GR00T N1.5 and 𝜋0.5, which use the default windows:
per-skill values from 62 to 476 control steps and a 299-step fallback for substages with no matching
skill. Xiaomi-Robotics-1, the development policy, uses a single 120-step window.
B.3. Harness VLA comparison protocol
Table 5, Panel A, uses the success rates tabulated in arXiv v5 of Zhang et al. (2026b). Appendix C.3,
Table 12 of that paper specifies five evaluation seeds per task (250 rollouts), and Appendix H reports
low reasoning effort for GPT-6 Astra. The authors’ released evaluation record lists 340 rollouts (180
atomic, 80 seen composite, and 80 unseen composite) and documents a correction of the Astra
reasoning effort to high. Both sources report 59.2% overall for Astra.
B.4. Failure audit
The audited failures come from an earlier RoboCasa365 evaluation of Xiaomi-Robotics-1 running
without a harness, which produced 2,413 valid rollouts, 893 of them failures. We sampled 193 failures
across five task groups (the atomic-seen, composite-seen, and composite-unseen tasks evaluated
in §4.1, all 65 atomic tasks, and tasks that appear only in the pretraining set), selecting up to 50
episodes per group and at most three per task. For each episode, we reviewed the instruction alongside
synchronized keyframes from three cameras and simulator records of object motion, gripper contact,
and appliance state. We labeled the earliest observable error that diverted the robot from the task. To
check consistency, we reannotated 45 episodes. Of the 44 episodes for which we assigned a definite
label on the second pass, 38 received the same primary label both times (86%).

B.5. Episode sets and their overlap
The shared 50-scene subset is contained in the main evaluation. Of the 80 episodes in the Sol
trajectory audit, 64 use main-evaluation scenes (episode indices 1–4 of the 16 unseen-composition
tasks) and 16 use episode index 0. The audit reads trajectories supervised by Sol, whereas the main
results use Astra. Of the 72 development episodes, 28 trace to failures included in the failure audit,
and 10 match main-evaluation scenes on the task, the initial simulator state, and the starting camera
images (§4.1).
B.6. What the harness knows about a task
We count as preparation anything made for one task that tells a harness how to solve it: demonstrations,
exploration episodes on that task, stored memories, or scripts. RoboHarness-Zero uses none of these.
Its rules and prompts contain nothing written for a particular task, and it keeps no memory between
episodes. The only prior information is the skill profile, which records how often and how quickly
the policy alone completes each skill and is measured without any VLM call (§3.7). The profile tells
the harness how much to trust the policy, not how to solve the task, and a skill without an entry
uses policy-wide defaults. This information overlaps with the evaluated tasks in three ways. The 65
profiled atomic tasks include the 18 atomic tasks we evaluate. Five of the 32 evaluated composite
tasks also have a whole-task entry in the profile, covering 20 of the 128 composite episodes. Finally,
we developed the rules on 72 episodes that cover 47 of the 50 tasks (§4.1).
B.7. Example episodes
An episode without intervention (§3.3). In one episode, the robot was asked to add a lemon wedge
and an ice cube to a glass of lemonade. At steps 160, 320, and 480, the VLM recorded that the gripper
had reached the refrigerator handle, the door had opened, and the gripper held the lemon wedge. It
continued to check every 160 steps through step 960. The policy completed the task at step 1,000
under the same instruction it had received at the start.
Handing over the whole task (§3.3). We adopted this rule after observing an early failure on a
tea-serving task. An earlier version split the task into moving a kettle, placing a mug on the same
tray, and closing the cabinet doors. It took over to move the kettle and later instructed the policy to
close the doors while the mug was still off the tray. On the same scene, the policy completed the full
sequence in 1,415 steps when given the original instruction from the outset.
Judging progress at the current substage (§3.4). A matched development run illustrates why the
scope of the progress signal matters. The robot had to place a loaf of bread in a basket and then
carry the basket to the dining counter. The earlier version of the harness repeatedly credited the
robot for holding the loaf as it drove through the kitchen. It was still reporting progress after the
basket had disappeared from view. By the time it flagged a placement failure at step 832, the robot
had released the loaf onto a bare counter. The two versions executed identical actions through step
320. At that checkpoint, the current version found no evidence that the loaf was getting closer to
the basket and prompted the policy to “Place the bread in the basket on the counter.” At step 512,
the wrist camera showed the loaf inside. The harness then advanced to moving the basket, and the
environment registered success at step 1,127.

when no measurement is available. The harness ends the attempt after 150 executed steps without

B.9. Harness VLA transfer evaluation
Our transfer evaluation used one scene per task and GPT-6 Astra at xhigh reasoning effort. The
published evaluation used multiple seeds per task (Appendix B). In the released memory set, four
of the 50 tasks (OpenCabinet, OpenDrawer, HeatKebabSandwich, and WashFruitColander) lack the
task-specific Markdown notes but keep their other task-specific files and the global memory. We
evaluated all four using the remaining released memory. Harness VLA and our harness each solve
three of these four scenes, and Xiaomi alone solves two. On the remaining 46 scenes, Harness VLA
solves 26, Xiaomi alone 28, and our harness 31.
None of the four scenes that Xiaomi solves alone and Harness VLA loses (CoffeeSetupMug, Get-
ToastedBread, KettleBoiling, and WaffleReheat) is among these four tasks. Both runs had the same
control-step limit in each scene. Xiaomi alone first succeeds at steps 209, 1,885, 1,211, and 1,216,
while the Harness VLA runs use the full limits of 600, 3,000, 1,500, and 4,050 steps without complet-
ing the task. They stop at different points: the mug is set down outside the valid position under the
dispenser, the toast is never taken out of the toaster, the kettle is left 0.30 m from the burner, and the
microwave is never switched on.
