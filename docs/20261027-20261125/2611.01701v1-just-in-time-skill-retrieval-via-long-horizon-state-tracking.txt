Abstract
Large language model (LLM) agents increas-
ingly rely on external skill libraries to support
complex task execution. However, determin-
ing which skills are needed remains challeng-
ing in long-horizon tasks. Existing methods
typically select a fixed skill set before execu-
tion, implicitly assuming that a task’s proce-
dural requirements can be determined from
its initial description. This assumption is re-
strictive for long-horizon interaction, where
new requirements emerge from intermediate
observations, execution outcomes, and newly
revealed constraints. This motivates just-in-
time skill retrieval, which dynamically selects
skills as execution unfolds. Just-in-time skill
retrieval is promising but challenging: the util-
ity of a skill depends not only on the current
context, but also on the evolving task state
shaped by prior steps. To this end, we pro-
pose JitSkill, a state-grounded framework that
addresses this challenge through continuous
task-state tracking. By connecting emerging
requirements with accumulated task progress,
JitSkill provides procedural support throughout
execution without treating each retrieval deci-
sion independently. Experiments across three
agent benchmarks demonstrate its effectiveness
in improving long-horizon task completion.
Our code is available at https://github.
com/XMUDeepLIT/JitSkill.git/.

Introduction
Large Language Model (LLM)-based agents in-
creasingly rely on external knowledge to support
complex reasoning, tool use, and interaction with
their environments (Feng et al., 2026; Zhou et al.,
2026b; Huang et al., 2026; Wu et al., 2026b; Yuan
et al., 2026; Jang et al., 2026). Among different
forms of external knowledge, skills provide a nat-
ural representation of procedural experience: they

†Corresponding authors.
capture how an agent accomplishes recurring goals
or operations by encoding successful task execu-
tions as reusable procedures that agents can invoke
again when similar demands arise (Xia et al., 2026;
Wu et al., 2026b; Yu et al., 2026). As these skills
accumulate across tasks, external skill libraries pro-
vide agents with a growing repository of procedu-
ral knowledge that can complement their underly-
ing reasoning and action capabilities (Wang et al.,
2023; Li et al., 2026d; Zhang et al., 2026).
As skill libraries continue to grow, exposing all
available skills to an agent becomes increasingly
impractical: it increases the context burden and
introduces irrelevant or only partially relevant pro-
cedures that may interfere with subsequent reason-
ing (Su et al., 2026; Li et al., 2025; Kang et al.,
2026). Existing approaches therefore largely for-
mulate skill selection as a retrieval problem, aiming
to identify a compact subset of useful skills from
an expanding skill library. Early retrieval-based ap-
proaches primarily identify individual skills accord-
ing to their relevance to the task, as exemplified by
SkillFlow (Li et al., 2025) and SkillRouter (Zheng
et al., 2026). More recent methods move beyond
independent skill matching by explicitly modeling
relationships among skills: GoS (Liu et al., 2026),
GoSkills (Zeng et al., 2026), and CaSKG (Li et al.,
2026f) exploit dependency, grouping, or causal re-
lations to retrieve and organize structurally related
skills. SkillAligner (Li et al., 2026c) further con-
siders compatibility after retrieval, identifying mis-
matches among retrieved skills, task requirements,
and execution interfaces and adapting skill frag-
ments accordingly. Together, these advances have
progressively extended skill retrieval from individ-
ual relevance matching to structured retrieval and
alignment, enabling agents to access increasingly
large and heterogeneous skill libraries.
Despite these advances, existing retrieval meth-
ods largely assume that the skills required for a task
can be sufficiently determined from the information

available before execution begins. This assumption
becomes increasingly restrictive in long-horizon
interactive tasks, where capability demands are not
fully specified by the initial instruction but emerge
progressively through intermediate observations,
execution outcomes, and newly discovered con-
straints (Yao et al., 2023; Zhou et al., 2024). A skill
set selected at the outset may therefore provide ad-
equate support for the initial task description while
failing to cover procedural needs that arise later in
the trajectory. This limitation has motivated a shift
toward just-in-time skill retrieval, where skills are
retrieved on demand as task execution unfolds. Re-
cent web and computer-use agents instantiate this
paradigm by dynamically identifying skill require-
ments from the current observation, subgoal, or lo-
cal execution context and retrieving corresponding
skills when those requirements emerge (Li et al.,
2026a; Chen et al., 2026). Rather than predicting
all necessary skills from the initial task description,
just-in-time retrieval allows the retrieved skill set to
evolve with execution, retrieving skills when their
corresponding needs actually become observable.
Just-in-time retrieval is promising but challeng-
ing. (i) Whether a skill is needed depends not
only on the current context but also on prior exe-
cution. The same observation or subgoal can call
for different procedural support depending on what
has already been accomplished, which resources
have been acquired, which attempts have failed,
and which requirements remain unresolved (Bai
et al., 2026; Zhou et al., 2026a; Xu et al., 2026). A
skill that is useful early in a trajectory may become
redundant once the requirement it addresses has
been satisfied, or even conflict with decisions estab-
lished later in execution. Consequently, retrieving
skills only from the current observation or local sub-
goal can produce individually reasonable decisions
that are inconsistent with the task’s accumulated
progress. (ii) Maintaining a task state that reliably
guides skill retrieval and execution is challenging.
Simply retaining the full history can obscure the
task-relevant consequences of prior interactions,
causing the agent to repeat completed work, revisit
invalidated paths, or overlook commitments that
should constrain subsequent skill decisions. To-
gether, these challenges create a fundamental risk
in just-in-time retrieval: locally relevant skills can
be repeatedly selected and successfully executed
without forming a coherent trajectory toward the
remaining task goals. We refer to this failure as
execution drift, which manifests as redundant ex-
ploration or execution-consistency deviation.
To address these challenges, we propose JIT-
SKILL, a state-grounded skill retrieval framework
that couples just-in-time skill retrieval with long-
horizon task-state tracking.
Rather than treat-
ing each retrieval decision as an independent re-
sponse to the current context, JITSKILL continu-
ously maintains a compact representation of the
task state and uses it to guide both skill retrieval
and subsequent execution. Specifically, it main-
tains complementary explicit and latent represen-
tations that together constitute the task state. The
explicit record organizes prior operations, their out-
comes, and failure feedback into accessible tex-
tual evidence, while the latent representation re-
currently summarizes historical interactions that
cannot be fully retained in bounded explicit fields.
At each decision point, the skill navigator grounds
just-in-time skill retrieval in the tracked task state
while responding to the current execution context.

Our contributions are as follows:
• We identify two limitations of existing skill
retrieval paradigms: fixed pre-execution skill
retrieval cannot cover demands that emerge
as a task progresses, while local online
matching cannot determine whether selected
skills remain consistent with accumulated task
progress. We show why treating each retrieval
decision as an independent response to the
current context leaves both unresolved.
• We introduce JITSKILL, a task-state-grounded
framework for just-in-time skill retrieval. It
tracks task progress through complementary
explicit and latent states, which guide on-
demand retrieval and are provided to the ex-
ecutor for state-aware skill execution.
• Across SkillsBench, ALFWorld, and τ 2-
Bench, JITSKILL achieves the highest over-
all task success rates, with a 20.6% relative
improvement over the strongest baseline on
SkillsBench. Ablation results further support
the benefit of jointly grounding skill retrieval
and execution in the tracked task progress.
2
Preliminary Study
We examine the limitations of fixed pre-execution
skill retrieval in long-horizon tasks, analyze how
online retrieval based on local execution context
affects task progress, and explore ways to capture
task-state information from interaction trajectories
by comparing full histories with structured history
records. Experimental details are in Appendix D.
Execution Requires Continually Updated Skill.
We compare Initial and Online Retrieval at the
same execution decision points using Hit@3,
which measures whether the top three retrieved
skills include a skill compatible with the stage-
specific need. Online Retrieval raises Hit@3 from
0.115 to 0.385.
This gap indicates that skills
retrieved from the initial instruction cannot ade-
quately cover procedural needs that become appar-
ent during execution. Intermediate observations
and execution outcomes provide additional infor-
mation about these needs, motivating retrieval that
can be updated as the task unfolds.
Skill Retrieval Based Solely on Local Context
Can Cause Execution Drift.
Figure 2a illus-
trates how similar local cues can require differ-
ent skill decisions depending on prior progress.
A passport-lookup skill helps satisfy a prerequi-
site before the ID is obtained, but becomes redun-
dant once a valid ID has been saved. Likewise, a
cheapest-fare skill may match a current offer while
conflicting with established departure-time or re-
fund requirements. Local relevance alone cannot
establish whether a skill is needed or consistent
with conditions accumulated during execution. At
the task level, Online Retrieval improves TGC over
Initial Retrieval by 2.9 and 5.6 percentage points
on D1 and D2, but decreases it by 2.1 points on
D3. Together with the coverage results, this shows
3


that making stage-relevant skills available does not
consistently translate into higher task completion,
motivating consideration of prior results and unre-
solved requirements in subsequent skill decisions.
Interaction Histories Require Careful Organiza-
tion into Task States.
We compare local-context
retrieval with two ways of incorporating prior in-
teractions: the full history and a short structured
record. Simply appending the full history does not
improve skill retrieval. Instead, it lowers Hit@3
from 0.385 to 0.346 while substantially increas-
ing query length, and leads to more execution-
consistency deviations (Figure 2c). In contrast,
a structured record that summarizes the task goal,
previously called interfaces, and observed failures
reduces both redundant exploration and execution-
consistency deviation compared with local-context
and full-history retrieval. These findings suggest
that the value of interaction history depends not on
how much is retained, but on how task-relevant in-
formation is organized. This motivates an evolving
task state that preserves prior execution outcomes
and constraints to guide subsequent skill decisions.
Takeaway.
These diagnostics motivate three de-
sign choices in JITSKILL. Skill retrieval should be
updated as new needs emerge, interaction history
should be organized into an evolving task state, and
this state should guide skill acquisition and execu-
tion. The state should identify missing procedures,
reusable results, failure conditions that warrant
avoiding repeated attempts, and constraints that
subsequent local cues should respect. JITSKILL
realizes this guidance through complementary ex-
plicit and latent representations, and provides both
of them to a resource-constrained executor.
3
The Framework of JITSKILL
In this section, we present JITSKILL, a framework
that grounds just-in-time skill retrieval and subse-
quent skill execution in a continuously tracked task
state. It maintains complementary explicit and la-
tent representations to retain task progress across
interactions. We first introduce the framework in
Section 3.1, then describe task-state tracking in
Section 3.2, and finally explain state-grounded skill
retrieval and state-aware execution in Section 3.3.
3.1
Overview
We consider long-horizon interactive tasks in which
an agent retrieves reusable skills from an external
library K = {k1, . . . , kN}. At decision point t,
the current execution context consists of the task
instruction u, the observation ot, and a bounded
recent interaction history Ht.
To retain task-
relevant execution information beyond this recent
context, JITSKILL maintains an evolving task state
St = (Bt, Zt). The explicit state Bt records in-
spectable task facts and execution outcomes, while
the fixed-size latent state Zt retains historical con-
text through recurrent updates. Together, they rep-
resent the accumulated task progress relevant to
subsequent skill decisions across execution steps.
As illustrated in Figure 3, a skill navigator se-
lects skills from the external library according to
the tracked task state and current execution context,
producing a skill set Kt ⊆K within the skill bud-
get. The executor combines these skills with the
current context, the explicit state Bt, and the pro-
jected latent state tokens Z′
t to generate the next ac-
tion at. The action and resulting environment feed-
back ot+1 inform subsequent updates to the task
state and recent context, closing the loop between
task-state tracking, just-in-time skill retrieval, and
state-aware execution over successive task steps.
3.2
Task-State Tracking
Task-state tracking organizes execution evidence
into complementary representations that provide
sufficient context for later decisions. The explicit
record organizes discrete task facts into a form that
can be directly inspected and updated during execu-
tion. The latent state complements these records by
continuously carrying forward context distributed
across the execution process, which is difficult to
predefine as a small set of fixed textual fields.
Explicit task state.
The explicit state Bt is a
bounded structured textual summary that continu-
ously records and updates important information
during long-horizon interaction. It preserves in-
spectable task facts, including key facts required
for task completion, important subtasks and their
progress, completed operations and their outcomes,
and failed attempts with their associated feedback.
To update Bt, we extract completed operations,
their outcomes, and observed failures from the in-
teraction history preceding the current decision,
denoted by H<t:
Bt = E(u, H<t),

3.3
State-Grounded Skill Decisions
JITSKILL uses the same task state to coordinate
skill retrieval and execution. It retrieves reusable
procedural knowledge that can advance the remain-
ing task requirements, and provides the same state
to the executor so that skill execution remains
aligned with global task progress. The following
components formalize these coupled decisions.
Progress-conditioned skill retrieval.
As execu-
tion unfolds, new skill requirements emerge from
5


intermediate observations and execution feedback.
Rather than treating retrieval as an isolated match
to local context, JitSkill retrieves skills that advance
the remaining task requirements under the tracked
task state. At each execution step, the navigator
ranks candidate skills by their consistency with the
tracked progress, then selects the currently needed
skill subset Kt from the skill library K. This al-
lows the retrieved skill set to evolve with newly
emerging needs while avoiding repetition of com-
pleted work, invalidated paths, and conflicts with
prior execution. Appendix C provides the complete
retrieval formulation and implementation details.
State-Aware Skill Execution.
Retrieval must be
coupled with skill execution: even a skill selected
based on the task state can be executed inconsis-
tently if the executor does not receive the state used
to select it. JitSkill therefore supplies the executor
with the same two-part state used for navigation.

lightweight projection Pψ, which maps the latent

Experiments
In this section, we conduct comprehensive experi-
ments to answer the following research questions:
RQ1 (Effectiveness). How effectively does JIT-
SKILL support long-horizon task execution com-
pared with existing skill-augmentation and agent-
execution methods? RQ2 (Ablation). How do
real-time skill retrieval, progress-conditioned skill
execution, and explicit and latent representations
contribute to task completion? RQ3 (Model Stud-
ies). How do skill injection settings affect task
performance, and how efficiently does JITSKILL
complete tasks? Further analyses appear in Appen-
dices F.5 and F.3.
4.1
Experimental Settings
Datasets.
We evaluate on SkillsBench (Li et al.,
2026d), ALFWorld (Shridhar et al., 2021), and τ 2-
Bench (Barres et al., 2025), covering containerized,
interactive household, and conversational tool-use
tasks, respectively.
Baselines.
We compare three groups: (i) direct
execution without skills, including Qwen3-8B and
Qwen3.8-27B; (ii) pre-execution skill retrieval, in-
cluding SkillTrace (Yao et al., 2026), SoftSkill (Tao
et al., 2026), CodeSkill (Li et al., 2026e), Skil-
lZip (Tan et al., 2026), StructAgent (Wu et al.,
2026a), and FlowState (Li et al., 2026b); and (iii)
execution-time skill retrieval, including SGDR (Li
et al., 2026a), WebXSkill (Wang et al., 2026), and
CUA-Skill (Chen et al., 2026).
Evaluation Metrics.
Following the official eval-
uators of the three benchmarks (Li et al., 2026d;
Shridhar et al., 2021; Barres et al., 2025), we re-
port task success rate (SR) and mean environment
interaction steps to assess task completion and in-
teraction efficiency.
Implementation Details.
Methods are evaluated
under shared execution and skill-access settings.
Hyperparameters are selected on training data only,
and results are averaged over three runs. Dataset
statistics, baseline adaptations, evaluation proto-
cols, and implementation configurations are de-
tailed in Appendices F.9, E.1, and E.2.

4.3
Ablation Studies (RQ2)
To isolate the contribution of each component in
JITSKILL, we ablate just-in-time skill retrieval,
progress-conditioned skill execution, the explicit
progress record, and the latent progress represen-
tation on AppWorld and ALFWorld. All variants
share the executor, skill library, training data, injec-

Related Work
Skill Retrieval. Early work on skill retrieval fo-
cuses on pre-execution selection. SkillFlow (Li
et al., 2025) employs multi-stage retrieval and fil-
tering, and SkillRouter (Zheng et al., 2026) further
incorporates procedural information from skill bod-
ies. Beyond individual skill matching, GoS (Liu
et al., 2026), GoSkills (Zeng et al., 2026), and
CaSKG (Li et al., 2026f) model skill dependen-
cies, groupings, and calibrated relations.
Skil-
lAligner (Li et al., 2026c) adapts retrieved skills
to task requirements and interfaces. However, pre-
execution retrieval may miss procedural needs that
emerge during interaction. SGDR (Li et al., 2026a)
and WebXSkill (Wang et al., 2026) dynamically re-
trieve skills based on the current execution context.
CUA-Skill (Chen et al., 2026) further incorporates
execution history into skill selection and configu-
ration. Nevertheless, local relevance alone does
not establish whether a skill remains necessary or
consistent with accumulated task progress.
State Management. Task-state management pro-
vides another line of research on long-horizon
agent execution. Existing methods address work-
flow control (Wu et al., 2024), progress verifi-
cation (Wu et al., 2026a), and state-aware tool
use (Yang et al., 2026; Guo et al., 2026). Other
studies focus on retaining information across in-
teractions.
FlowState (Li et al., 2026b) pre-
serves execution evidence for later reuse, whereas
SKILL.state (Badhe et al., 2026) maintains struc-
tured state to support the execution of selected
skills. Further related work appears in Appendix B.
6
Conclusion
In this paper, we formulate just-in-time skill re-
trieval for long-horizon agents, acquiring skills on
demand as task requirements emerge during execu-
tion. Fixed pre-execution retrieval can miss later
needs, while local-context retrieval can overlook
accumulated task progress and lead to execution
drift. We propose JITSKILL, which maintains com-
plementary explicit and latent task states to make
skill selection task-progress-aware rather than an
independent local match, jointly guiding skill re-
8


trieval and the subsequent use of retrieved skills.
Experiments across three long-horizon benchmarks
show JITSKILL consistently outperforms baselines,
with a 20.6% relative improvement over WebX-
Skill on SkillsBench. These results underscore the
value of tracking evolving task progress for coher-
ent long-horizon skill retrieval and use.
Limitations
JITSKILL assumes an execution interface that ex-
poses step-wise observations and supports repeated
skill retrieval during task execution. Its effective-
ness may be limited when feedback is sparse or
delayed, when the available skill library does not
contain the capabilities required by the task, or
when the maintained execution state cannot capture
the information needed to distinguish competing
skills. The current evaluation focuses on API-based
and containerized agent environments; extending
the framework to settings with richer perceptual ob-
servations, unreliable tools, or human-in-the-loop
interaction remains an important direction for fu-
ture work.

Frequently Asked Questions
A.1
What are the advantages of JITSKILL?
Existing skill-augmented agents either fix the skill
set before execution or retrieve skills from the cur-
rent local signal, such as the latest observation or
a summary of the current state. Neither tells the
agent whether a seemingly relevant skill fills an un-
met requirement, repeats completed work, or con-
flicts with earlier execution. JITSKILL maintains
an evolving task-progress state, consisting of an ex-
plicit progress record and a latent state, and uses the
same state both to select skills and to condition the
executor that applies them. As a result, the selected
skills follow the stage of the task (Appendix F.11
and Appendix G), and JITSKILL achieves the best
success rate on SkillsBench and ALFWorld under
the same executor and skill budget (Table 1).
A.2
Why maintain both an explicit record and
a latent state?
The two representations carry complementary in-
formation. The explicit record keeps discrete, in-
spectable facts such as completed operations and
failed attempts, whereas the latent state carries
cross-step context that is difficult to enumerate as
fixed textual fields. Removing either one lowers
performance on both ALFWorld and AppWorld
(Figure 6), so the full state is needed for the best
result.
A.3
Does JITSKILL benefit from a larger
context than the baselines?
No.
All skill-augmented methods deliver their
skills at the same prompt location under the same
per-step budget, and the explicit record of JIT-
SKILL is counted within this budget. JITSKILL
changes which skills are delivered, not how much
text is delivered: it switches skills more often than
step-wise retrieval while every injected block stays
within the budget (Appendix F.11), and it com-
pletes ALFWorld games in fewer steps than the
no-skill agent and SGDR (Appendix F.4).
A.4
How are the baselines made comparable?
Each baseline is re-implemented under one shared
protocol: the same frozen executor, skill library, re-
trieval backbone, injection location, and skill bud-
get. Each method follows the default configura-
tion of its paper, any extra model call it requires
is issued to the same executor, and every hyper-
parameter is selected on official training data only
(Appendix E.1).
A.5
How sensitive is JITSKILL to its
hyper-parameters?
JITSKILL stays above 89% on ALFWorld for every
number of injected skills from 1 to 5, and a mod-
erate skill budget already reaches the best success
rate (Appendix F.3). The weights of the training
objective lie on a flat optimum (Appendix F.5).
A.6
Does JITSKILL generalize beyond the
evaluation setting?
Yes. Without re-tuning, JITSKILL matches the
highest success rate on unseen ALFWorld envi-
ronments (Appendix F.7). With a weaker Llama-
3.1-8B-Instruct executor, it achieves the highest
success rate, whereas step-wise retrieval falls below
the no-skill agent; the navigator remains unchanged
and any executor-side interface is trained on official
training trajectories only (Appendix F.6).
B
Related Work
B.1
Pre-Execution Skill Preparation
Some studies treat skill augmentation as prepara-
tion before execution, acquiring relevant skills from
an external library based on initial task require-
ments to provide procedural support for subsequent
execution. SkillFlow (Li et al., 2025) uses multi-
stage retrieval and filtering to obtain a compact skill
set from a large library. SkillRouter (Zheng et al.,
2026) further incorporates procedural information
from skill bodies, addressing the limitations of as-
sessing relevance from names and short descrip-
tions alone. Since the relevance of individual skills
does not guarantee that the resulting set supports
complete execution, Graph-of-Skills (GoS) (Liu
et al., 2026) incorporates skill dependencies into
retrieval to recover prerequisites that might other-
wise be missed. GoSkills (Zeng et al., 2026) ex-
tends the retrieval unit to role-labeled skill groups
and presents the selected skills through Start, Sup-
port, Check, and Avoid fields, helping the executor
understand how they work together. CaSKG (Li
et al., 2026f) calibrates skill relations through coun-
terfactual probes, allowing graph-based retrieval
to expand the retrieved skill set along more reli-
able procedural relations. Beyond improving the
acquired skill set, SkillAligner (Li et al., 2026c)
jointly adapts retrieved skills before execution, spe-
cializing skill fragments to task requirements and
available interfaces, resolving dependencies, con-
12


flicts, and redundancy, and producing a guide for
subsequent execution. Starting from initial require-
ments, these methods improve the relevance, com-
pleteness, and applicability of the skills available
when execution begins. However, the capability
demands of long-horizon tasks often emerge grad-
ually through environmental feedback, while ac-
quired resources and newly discovered constraints
change the procedural support needed later. Our
work focuses on these changes during execution,
continuously maintaining task progress so that skill
acquisition and execution can adapt together to the
remaining requirements.
B.2
Skill Acquisition and Use During
Execution
As interaction environments and capability de-
mands change during execution, some web and
computer-use agents dynamically acquire skills
and execute them while a task is in progress (Xi-
ang et al., 2026). SGDR (Li et al., 2026a) extracts
reusable subprocedures of intermediate granular-
ity from completed trajectories, representing their
purpose in natural language and providing oper-
ational support through code.
It combines the
task goal with the current webpage state to re-
trieve skills at each step, rather than restricting
skill execution to a fixed set selected at the start
of the task. WebXSkill (Wang et al., 2026) iden-
tifies currently available skills from URL patterns
and page elements, uses task and page context for
semantic matching across websites, and provides
both callable action sequences and step-level guid-
ance to support direct execution or agent-controlled
actions. These mechanisms emphasize matching
skills to the current environment. However, lo-
cal page conditions or semantic similarity do not
fully capture previously completed work and es-
tablished constraints, and the same page may call
for different operations at different stages of a task.
Consequently, locally relevant skills may still lead
an agent to repeat completed exploration or pro-
ceed before prerequisites have been satisfied. CUA-
Skill (Chen et al., 2026) represents computer oper-
ations as parameterized skills and execution graphs.
It reinitializes memory for each task and uses this
memory to provide execution history for skill se-
lection and argument configuration, helping the
agent determine how to complete the current oper-
ation successfully in the current interface. Within
skill configuration and execution, the emphasis is
on reliably carrying out an already selected oper-
ational skill. Our work instead examines whether
that skill still contributes to task progress, continu-
ously maintaining task progress to jointly condition
subsequent skill acquisition and execution.
B.3
Execution Management for Long-Horizon
Task
Maintaining completed work, unmet requirements,
and existing constraints can help agents reduce er-
rors in assessing task progress and improve the
consistency of subsequent decisions during long-
horizon interaction. To improve execution con-
trollability, StateFlow (Wu et al., 2024) organizes
complex tasks into states and transitions, distin-
guishing workflow progression from task solving
within each stage so that operations follow explicit
execution stages. Rather than primarily control-
ling workflow progression, StructAgent (Wu et al.,
2026a) focuses on whether an agent has sufficient
evidence to conclude that a task has made progress.
It confirms state changes through verification, pre-
venting attempted operations from being treated as
completed work and supporting task-completion
judgments and failure recovery. It also introduces
relevant operational experience at subgoal transi-
tions, while emphasizing verifiable progress, error
localization, and recovery. To address failures to
carry historical information into subsequent opera-
tions, NOD (Yang et al., 2026) combines explicit
task state with critical-action review, while OODA-
Tool (Guo et al., 2026) separates state reconstruc-
tion from action generation through staged process-
ing. Both aim to reduce the neglect of existing
requirements and constraints in tool calls, focusing
on operation correctness and consistency with task
state during multi-turn interaction. Considering the
reuse of historical information in later interactions,
FlowState (Li et al., 2026b) observes that some
information becomes relevant only when subse-
quent subtasks or requests arise, whereas repeated
context compression can discard it prematurely. It
therefore preserves execution states and associated
evidence as memory reusable across requests and
revisits them when new decisions require them, ad-
dressing the trade-off between persistent informa-
tion retention and working-context cost. Compared
with these approaches to general agent execution,
SKILL.state (Badhe et al., 2026) directly addresses
long-horizon execution after a skill has already
been selected. To mitigate growing interaction his-
tories and interference from obsolete information,
it replaces accumulated conversation records with

Method Details
This appendix details the recurrent encoder, its
history-compression pretraining objective, the nav-
igation fine-tuning objective and skill scoring used
in our experiments, and the training configuration.
C.1
Recurrent Encoder
The latent representation uses m = 16 slots. The
encoder fθ is a frozen base language model adapted
with LoRA: at each step it reads the previous rep-
resentation Zt, the token embeddings of the newly
accumulated interaction Dt+1, and m learnable
slots, and the outputs at the slot positions form
Zt+1. The initial representation and the learnable
slots are trained together with the LoRA weights.
Each update reads only the previous representation
and the new block, so the per-step cost does not
grow with trajectory length.
To match history integration at inference, train-
ing constructs successive history blocks along each
trajectory and passes the representation from one
step to the next. Forward computation preserves
this recurrent dependency, while gradients are trun-
cated across steps, which keeps the memory cost
of training independent of trajectory length.
C.2
History-Compression Pretraining
The first training stage pretrains the encoder to re-
tain historical content, support its subsequent use,
and keep different histories distinguishable. We
constrain content recovery through reconstruction,
subsequent prediction through distribution align-
ment, and distinctions between histories through
representation contrast.

(y1, . . . , yn), a frozen decoder predicts each token

C.3
Navigation Objective and Skill Scoring
The navigator gϕ maps the slot-averaged latent rep-
resentation and a sentence embedding of the ex-
plicit record Bt to a query vector qt. Each skill
k ∈K is scored by the similarity between qt and
the embedding of its description, which defines
pθ,ϕ(k | Zt, Bt) through a softmax over the library.
At inference, this learned score is combined with
the relevance of each skill to the current step, and
the top-ranked skills are injected within the skill-
injection budget CK.
The second training stage initializes the encoder
with the pretraining checkpoint and jointly fine-
tunes it with the navigator on execution trajectories
from the official training split. For each decision
point, the supervision target is the set of skills that
support the next action, determined from the opera-
tions the trajectory executes at that step. The target
yi,t in Equation 4 spreads unit mass uniformly over
this set, and decision points with no supporting
skill are skipped. This objective jointly updates
the encoder and navigator in all experiments. For
benchmarks whose skill library differs from the
training library, we use a scoring head that reads
skill descriptions directly; it is trained on the same
AppWorld training trajectories and applies to a new
library without retraining.

Retrieval conditions.
Initial Retrieval retrieves
skills from the initial task instruction before ex-

state mechanism of JITSKILL.

D1, D2, and D3 correspond

Experimental Setup Details
E.1
Baselines
Each external method is re-implemented under the
shared protocol of Section 4: the same skill library,
retrieval backbone, executor, injection location, and
per-step skill budget. Published end-to-end scores
from web or desktop environments are therefore
not transferred; the comparison isolates the deci-
sion rule that determines when and which skills
reach the executor. Table 2 groups the baselines
by this decision rule: pre-execution retrieval, re-
trieval from the current local signal, and retrieval
conditioned on a maintained execution state.
E.1.1
CUA-Skill
CUA-Skill (Chen et al., 2026) is a computer-use
skill framework that represents reusable desktop op-
erations as parameterized execution graphs. During
execution, its planner generates retrieval queries
from the user instruction, the current user-interface
state, and an execution-memory buffer; it retrieves
and re-ranks candidate skills, instantiates the argu-
ments of the selected skill, and executes the result-
ing operation. Its memory buffer is initialized from
the task instruction and then appends a concise
summary of each executed skill and its observed
outcome. The buffer therefore exposes prior suc-
cesses, failures, and their contexts to later retrieval,
re-ranking, and argument-instantiation decisions.
CUA-Skill addresses a complementary but dif-
ferent problem from JITSKILL. Its parameteriza-
tion and execution graphs aim to make a selected
computer-use operation executable in the current
interface. For example, argument instantiation fills
operation-level slots such as a target UI element
or coordinate, input text, file path, or application-
specific option; the memory buffer helps the plan-
ner avoid repeating unsuccessful operations and re-
cover from execution failures. These mechanisms
improve how an already selected skill is instanti-
ated and executed under local interface conditions.
In contrast, JITSKILL addresses whether a skill
should remain part of the task-level decision pro-
cess as execution progresses. It maintains task-
progress state that distinguishes unresolved require-
ments, satisfied conditions, reusable resources,
failed routes, and active commitments. This state
determines whether external support should be
newly retrieved, whether previously available sup-
port should be reused or skipped, and whether a
locally executable skill is compatible with the re-
maining task constraints. Thus, successful oper-
ation execution alone is insufficient: a skill can
be correctly configured and executed while being
redundant after a requirement has been satisfied,
or inconsistent with a commitment established ear-
lier in the trajectory. We include CUA-Skill as a
strong execution-time retrieval baseline to distin-
guish operation-level execution support from task-
progress-grounded skill lifecycle control.
E.1.2
Reproduced Baselines
All reproduced baselines run under the shared pro-
tocol: the same frozen executor, the same skill
library, the same injection location, k = 3 skills
per step, and the same skill-injection budget CK.
Each follows the default configuration of its paper,
and any extra model call a method requires is is-
sued to the same executor. To keep the retrieval
19


backbone identical across methods, every method
embeds skills with all-MiniLM-L6-v2.
SGDR.
At each step, the executor writes a short
summary of the current state. Each skill is scored
by a weighted combination of its similarity to the
task goal and to this state summary (weight 0.5),
and the shortlisted skills are selected by maximal
marginal relevance (λ = 0.7).
SkillTrace.
Once per task, the instruction is de-
composed into atomic sub-queries. Sub-queries
are matched to skills by optimal bipartite assign-
ment, and supporting skills are added by reverse
personalized PageRank over the skill input–output
dependency graph (restart probability 0.2, 50 it-
erations, 8 linking candidates, linking threshold
0.6). Matched skills are injected first, followed by
supporting skills in PageRank order.
WebXSkill.
We follow its guided mode. Candi-
date skills are retrieved by embedding similarity in
place of its URL-pattern graph, which has no coun-
terpart outside web navigation, and the selected
skill’s step-by-step guidance is injected at the fol-
lowing decision points.
SkillZip.
Each skill is segmented by the executor
into sections, each labeled with one of the nine
execution roles. At the start of a task, sections and
skills are seeded by reciprocal rank fusion against
task anchors, missing core roles (intent, operation,
verifier) are filled in, and the selection is rendered
at the finest level of detail that fits the budget. Motif
mining is omitted because the 37-skill ALFWorld
library contains no repeated cross-skill motifs.
FlowState.
At each step, the executor emits a
state delta (add, update, or remove) over typed
state nodes (preferences, knowledge, attributes,
judgments, and artifacts) following its protocol;
validated deltas are committed to the active state,
whose summary serves as the retrieval query. The
injected block contains the active state and the re-
trieved skills.
StructAgent.
The task is first decomposed into
requirements, all marked pending. At each step, a
verifier call reads the latest observation and marks
requirements as verified or invalidated; only the
verifier changes requirement status. The first pend-
ing requirement serves as the current subgoal for
skill retrieval, and the block contains the require-
ment table, the subgoal, and the retrieved skills.
Textual observations replace its GUI probes.
SoftSkill.
Each ALFWorld task type receives 32
trainable virtual tokens, initialized from the embed-
dings of the corresponding skill description and
trained with next-token prediction on successful
trajectories from the official training split, with
the executor frozen. Trajectories from the shared
executor replace the original teacher model. The
checkpoint is selected by success rate on held-out
training games, and the virtual tokens are attached
to the task turn through the serving engine’s em-
bedding interface.
CodeSkill.
The shared executor converts the skill
library into CodeSkill’s skill format and produces
add, merge, and drop maintenance decisions over
training-split trajectories; a Qwen3-8B skill man-
ager is fine-tuned on these decisions with LoRA
(rank 16, learning rate 10−4, two epochs), rebal-
ancing non-empty decisions so that the manager
does not default to no-op. At evaluation time, the
manager maintains the library online after each
game, and skills are retrieved through task-level
and event-level queries. We use the supervised
stage of CodeSkill.
All reproduced methods share the same per-step
skill budget CK, so every injected block has the
same size limit.
SKILL.state.
The append-only history is re-
placed by the triple of a procedural specification,
a structured execution state, and the latest obser-
vation. The executor returns a state patch together
with its action; the patch is validated against the
state schema (up to three attempts, with the rejec-
tion returned to the executor) and merged into the
state. The procedural specification is retrieved once
from the task instruction.

F.1
Dynamic Execution-State Maintenance on
ALFWorld
Dynamic execution-state maintenance is a natural
strategy for long-horizon agents: it records what
has happened so that later decisions need not re-
construct task progress from the entire interaction
history. The methods differ, however, in what their
state represents and in whether it conditions sub-
sequent skill retrieval and execution. Table 6 com-
pares the dynamic state-maintenance methods un-
der the common ALFWorld protocol.
State representations provide different deci-
sion signals.
StructAgent maintains verifiable re-
quirement status, and FlowState preserves state–
evidence pairs for later reuse. SKILL.STATE re-
places the history with a procedural specification,
a structured state, and the latest observation, but re-
trieves its procedural specification only once from
the initial task instruction. Their overall success
rates range from 52.38% to 86.19%.
Progress-grounded retrieval and execution are
complementary.
JITSKILL reaches 92.38% by
maintaining both an explicit progress record and
a latent progress representation, then using the
shared state to condition both which skills are re-
trieved and how the executor applies them. This
comparison indicates that retaining execution state
alone is insufficient when skill decisions must re-
main consistent with completed work and unre-
solved requirements.
F.2
Performance by Task Difficulty
To examine where state-grounded skill retrieval
matters most, we split the AppWorld frozen-
executor results by the benchmark’s own difficulty
field into difficulty levels 1, 2, and 3 (57 / 48 / 63
tasks). The labels are read from task metadata, so
no method can relabel its own tasks. Table 7 reports
task goal completion in each group.
The advantage of JITSKILL grows with task
difficulty.
JITSKILL is the strongest method in
every group, and its margin over step-wise retrieval
widens from +1.2 at difficulty level 1 to +5.6 at
difficulty level 2 and +9.0 at difficulty level 3. This
pattern indicates a larger benefit from tracked task
progress in the higher-difficulty group.
Local retrieval degrades at difficulty level 3.
Step-wise retrieval helps at difficulty levels 1 and 2
but falls below the no-skill agent at difficulty level
3 (55.6 vs. 61.9), and removing the task instruction
from its query drops it further to 48.7. These re-
sults indicate that local retrieval is insufficient to
improve completion in the highest-difficulty group,
whereas JITSKILL remains above the no-skill agent
in every group.
Appending more history is not a substitute for
tracked state.
Adding the raw textual history
or the full history to the retrieval query does not
recover the loss at difficulty level 3 (57.7 and 56.1),
and the full history even reduces completion at
difficulty level 2 to 65.3. These results show that
adding historical context alone does not resolve
this performance gap; JITSKILL instead conditions
retrieval on a compact state of task progress and
reaches 64.6 at difficulty level 3.
F.3
Sensitivity to the Number of Skills and the
Injection Budget
We study the two hyper-parameters that control
how many retrieved skills reach the executor: the
number of injected skills k and the injection bud-
get CK. We vary k at the default budget and CK
at the default k on ALFWorld, keeping all other
settings fixed (Figure 9): k = 1, 3, 5 reach 89.05%,
92.38%, and 89.76%, and CK = 600, 1,200, and
2,400 reach 84.05%, 92.38%, and 92.38%.
JITSKILL is robust to the number of injected
skills.
The default k = 3 performs best (92.38%),
and every setting from k = 1 to k = 5 stays above
89%. Because the navigator ranks skills against the
tracked task state, the most relevant skill is already
at the top of the list: with a single skill, JITSKILL
still reaches 89.05%.
A moderate budget suffices.
Halving the bud-
get to CK = 600 lowers success to 84.05%, be-
cause the progress record and one skill document
no longer fit together and the procedure is cut short.
Doubling it to CK = 2,400 brings no further gain
(92.38% in both cases): once the skills that match
the current stage are delivered in full, additional
procedural text adds nothing. The navigator there-
fore makes efficient use of a moderate budget, and
we use CK = 1,200 in all comparisons so that
every method operates under the same budget.

F.8
Trajectory-level Diagnostics
Beyond task completion, we examine how execu-
tion unfolds on AppWorld with two trajectory-level
measures. Action calls per solved task divides the
average number of API calls per episode, exclud-
ing documentation lookups, by the fraction of tasks
completed, so it measures how much execution ef-
fort each success costs. Completion after feedback
is the fraction of episodes that still complete the
task after encountering at least one error observa-
tion, which reflects whether execution returns to
the main line once something goes wrong.
JITSKILL spends the least effort per success.
JITSKILL needs 27.4 action calls per solved task,
13% fewer than the no-skill agent and 16% fewer
than step-wise retrieval. Tracked progress keeps the
executor from repeating operations it has already
completed.
JITSKILL recovers best after errors.
After an
error observation, JITSKILL still completes 72.8%
of episodes, whereas both retrieval baselines re-
cover less often than the no-skill agent (68.8% and
64.2%), and appending raw textual history low-
ers recovery further (62.7%). Because the explicit
record retains failed actions, the navigator can steer
the executor toward skills that address the failure
instead of retrieving support for the action that just
failed.

The three benchmarks impose different re-

embodied tasks, so the challenge is to retrieve the

task. SkillsBench ships a much larger library (195

with a simulated user, where the relevant procedure
changes as the dialogue moves from verification to
lookup to the requested modification.

[SKILL] alfworld−appliance−navigator
Navigates the agent to a target appliance (microwave, stove, fridge, or
sinkbasin) needed for object processing. Use when you are holding an
object that needs heating, cooling, or cleaning and must move to the
correct appliance station. Identifies the required appliance from the task
context and executes the movement action.
# Instructions
Use this skill when you are holding an object that needs to be processed
(heated, cooled, or cleaned) and you must locate and move to the correct
appliance to perform the action.
## Workflow
1. **Identify the Target Appliance:** Determine which appliance is
required for the task. Map the action to the appliance: ‘heat‘ −>
microwave/stoveburner, ‘cool‘ −> fridge, ‘clean‘ −> sinkbasin.
2. **Locate the Appliance:** Scan the environment observation for the
target appliance (e.g., ‘microwave 1‘, ‘fridge 1‘, ‘sinkbasin 1‘).
3. **Navigate:** Execute ‘go to {appliance}‘ to move to the identified
appliance location.
4. **Prepare Appliance (if needed):** Upon arrival, check if the
appliance requires preparation (e.g., opening a closed microwave or
fridge door). If so, perform ‘open {appliance}‘ before proceeding.
## Example
**Scenario:** You are holding ‘potato 1‘ and need to heat it.
Thought: I need to heat this potato. The microwave is the appropriate
appliance.
Action: go to microwave 1
Observation: The microwave 1 is closed.
Thought: I need to open the microwave before I can use it.
Action: open microwave 1
Observation: You open the microwave 1. The microwave 1 is open. In
it, you see nothing.
**Result:** You are now at the open microwave, ready to heat the
potato.
## Key Principles
−**Trigger:** The agent is holding an object and the next step in the
task is to ‘heat‘, ‘cool‘, or ‘clean‘ it.
−**Core Action:** The primary output of this skill is the navigation
command ‘go to {target_appliance}‘.
−**Prerequisite Check:** Always ensure the appliance is accessible (e.
g., open) before attempting to use it for processing.
[SKILL] alfworld−object−heater
Heats a specified object using an available heating appliance (e.g.,
microwave, stoveburner). Use when you are holding an object that
requires heating and need to navigate to and operate the heating
appliance. Takes the object and appliance as inputs and results in the
object being in a heated state.
# Instructions
Heat an object you are holding using a compatible heating appliance (
microwave or stoveburner).
## Prerequisites
−The target object must be in your inventory
−A heating appliance (microwave, stoveburner) must exist in the
environment
## Workflow
1. **Navigate:** ‘go to {appliance}‘ (e.g., ‘go to microwave 1‘)
2. **Check state:** If observation says appliance is closed, execute ‘
open {appliance}‘ −−verify observation confirms it is now open
3. **Heat:** ‘heat {object} with {appliance}‘ −−verify observation
confirms "You heat the {object}"
4. **(Optional) Place:** If the task requires it, navigate to the
destination and place the heated object
## Action Format
−‘go to microwave 1‘ / ‘go to stoveburner 1‘
−‘open microwave 1‘
−‘heat {object} with {appliance}‘ (e.g., ‘heat potato 1 with microwave
1‘)
## Error Recovery
−"Nothing happened" on heat: Check (1) you are holding the object, (2)
appliance is open, (3) appliance name is correct
−Appliance occupied: Take the existing item out first, then retry
## Example
**Scenario:** You are holding ‘potato 1‘ and need to heat it.
Thought: I need to heat the potato. I’ll go to the microwave.
Action: go to microwave 1
Observation: The microwave 1 is closed.
Action: open microwave 1
Observation: You open the microwave 1. The microwave 1 is open. In
it, you see nothing.
Action: heat potato 1 with microwave 1
Observation: You heat the potato 1 using the microwave 1.
**Result:** The potato is now heated. Proceed to place it at the
destination if required by the task.
